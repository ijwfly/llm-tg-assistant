# PROJECT_SPEC — нативное управление сессиями Claude Code через Telegram

Status: фаза 5 из 9 done — разрешения, вопросы и планы кнопками, tests green; фаза 6 (сессии и темы) не начата

Документ объединяет идеи двух референсов — `reference_spec_claude_code.md` (мост claude-tg:
тема форума = сессия Claude Code) и `reference_spec_tg_ux.md` (нативный чат-UX для LLM в
Telegram) — в одну целостную спецификацию нового проекта. Это исполняемый чек-лист работы:
по нему пишутся фазные спеки и код. Термины Telegram и Claude Code (reply, forward, draft,
tool call, topic, resume) оставлены английскими.

## 1. Зачем и что строим

### 1.1 Проблема

Claude Code живёт в терминале на сервере. С телефона к нему нужно ходить через ssh, а
официальный Telegram-плагин (channels) даёт одну интерактивную сессию, без управления
жизненным циклом, без вопросов и подтверждения планов в `-p`-режиме и с чужим UX.
Референс claude-tg решает многосессионность, но показывает ответ «как получится»:
частичный markdown, без стриминга в само сообщение, без диффов, без вопросов модели, без
планов. Референс tg_ux показывает, каким может быть по-настоящему нативный чат-UX, но не
про Claude Code.

### 1.2 Результат

Демон (бот) на Python, который:

- держит **одну сессию Claude Code на тему** Telegram (форум-супергруппа или личный чат с
  включёнными topics), сколько угодно тем параллельно;
- принимает всё, что человек естественно отправляет в чат (текст, фото, альбом, файл,
  голос, форвард, reply, правку), и превращает это в **один ход** Claude Code;
- показывает работу модели **в самом чате**: живой draft с размышлениями и следом
  инструментов, ответ полноценным markdown (заголовки, таблицы, код, диффы), вопросы
  модели — кнопками, план — карточкой с кнопкой «выполнять», запрос разрешения — карточкой с
  диффом и кнопкой «всегда»;
- управляет сессией из чата: новый контекст, стоп, отмена, повтор, resume любой сессии (в
  том числе из терминала), fork в новую тему, смена директории/модели/прав/усилий,
  персона, голос;
- **гарантирует доставку**: всё исходящее идёт через outbox в БД, переживает перезапуск,
  уважает лимиты Telegram.

### 1.3 Принципы (адаптированы из tg_ux)

1. **Чат — это интерфейс.** Никаких визардов и «режимов ввода». Жест Telegram определяет
   смысл: reply — «про это сообщение», forward — «положи в контекст», голос — «это текст»,
   документ — «вот файл», кнопка Stop — «хватит», новая тема — «новая сессия».
2. **Единица работы — батч, а не сообщение.** Всё, что пришло в тему за короткое окно,
   становится одним ходом и получает один ответ.
3. **«Запомнить» и «ответить» — разные вещи.** Форварды и файлы без подписи копятся в
   staging темы и уходят с ближайшим вопросом; бот не отвечает на них, а только квитирует
   реакцией.
4. **Транспорт доставляет, Claude Code думает.** Демон сам решает, что и как показать; модель
   не выбирает, отправлять ли ответ. Единственный инструмент моста для модели — «отправить
   файл».
5. **Тема = сессия.** Session id, директория, процесс, настройки и очередь — всё привязано к
   `(chat_id, thread_id)`. Темы независимы; внутри темы ходы строго по порядку.

### 1.4 Что осознанно не переносим из референсов

| Идея референса | Почему нет |
|---|---|
| Дерево истории по reply, «воскрешение ветки», окно устаревания 1 ч (tg_ux §7) | Контекст хранит Claude Code в транскрипте; ветвление даёт `/branch` (fork) в новую тему. Reply внутри темы — только цитата. |
| Собственная суммаризация (tg_ux §8) | Claude Code компактит сам (`/compact` и автокомпакт). |
| Image-proxy с токенами в имени файла (tg_ux §5) | Картинка уходит в Claude Code как base64 image block в stream-json. |
| Роли STRANGER…ADMIN, онбординг через админ-чат (tg_ux §12) | Бот даёт shell на машине; доступ — только явный `ALLOWED_USERS`. Онбординг — открытый вопрос (раздел 11). |
| `/usage_all`, тарифы моделей в конфиге | Стоимость берём из `result.total_cost_usd` Claude Code, когда он её сообщает. |
| Rust-демон, конфиг TOML, `claude-tg init` (claude-tg §11) | Стек проекта: Python, `settings.py`, docker-compose (CLAUDE.md §6–7). |
| Собственный MCP-сервер разрешений как единственный инструмент (claude-tg §7.1) | Тот же сервер, но с добавлением `send_file`. |

## 3. Решения

| Вопрос | Решение |
|---|---|
| Стек | Python 3.12, aiogram 3.31+, PostgreSQL 16 (asyncpg), pytest (`asyncio_mode=auto`). Без Agent SDK для запуска процессов; пакет `claude-agent-sdk` — только как библиотека чтения индекса сессий (при провале эксперимента 7 — свой парсер `projects/`). |
| Единица работы | Тема = сессия. Форум-супергруппа с Topics **и** личный чат с включёнными topics (рекомендуемая установка: личка + topics → и темы, и drafts). Личка без topics и группа без Topics — одна сессия на чат, `/project` недоступен. |
| Процесс | Один долгоживущий `claude -p …` на тему; ходы подаются в stdin по очереди; гасится по простою; поднимается через `--resume`. Отмена = SIGINT: CLI закрывает ход и выходит (spike 4), следующий ход поднимает процесс через `--resume`. |
| Разрешения | Режим `prompt` моста = `--permission-mode default` + `--permission-prompt-tool mcp__tgbridge__approve`. MCP-сервер `tgbridge` — stdio-процесс из репозитория, ходит в демон по unix-сокету. |
| «Всегда» | CLI не присылает suggestions (spike 1), поэтому правило строит мост по таблице §4.6.3 и возвращает его в `updatedPermissions` с `destination=localSettings`: правило попадает в `.claude/settings.local.json` репозитория, действует и в терминале, переживает перезапуск процесса. Мост ведёт учёт добавленных им правил (`topic_rules`) для `/perm` и `/perm forget`. |
| Вопросы модели | `AskUserQuestion` → карточки с кнопками, по одной на вопрос; «✍ Свой ответ» — следующее текстовое сообщение темы. |
| Планы | `ExitPlanMode` → rich-карточка с планом и кнопками «Выполнять (acceptEdits)», «Выполнять, спрашивать про правки», «Доработать план». |
| Входной конвейер | Батчер 300 мс на тему, сортировка по `message_id`, один ход на батч. Форварды и документы без подписи — в staging темы, отвечать не нужно; квитанция — реакция 👀. |
| Медиа | Фото — base64 image block **и** файл в inbox (для Read); документы/аудио — путь в inbox + пометка; голос → STT-команда → эхо 🎤. |
| Вывод | Rich Markdown как есть; fallback в plain при отказе парсера. Личка: живой `sendRichMessageDraft` с `<tg-thinking>` (строка прогресса, хвост размышлений, хвост текста), `can_stop`. Группы: сообщение-прогресс с кнопкой 🛑 и edit-in-place. Финал — rich-сообщения по естественным границам; fence-aware сплиттер; очень длинный ответ — файлом. |
| Инструменты моста | MCP-сервер `tgbridge`: `approve` (служебный, prompt tool) и `send_file` (модель отправляет файл в тему; доставку делает демон). Больше ничего. |
| Системный промпт | Короткая преамбула моста (`bridge_preamble.md`: «ты в Telegram, файлы пользователя тут, для отправки файлов есть send_file, формат под телефон») + опциональная персона SOUL. Оба через `--append-system-prompt-file`. |
| Сессии | `/sessions`, `/resume`, `/branch` (fork в **новую тему**), `/new`, `/rename` (имя сессии и темы синхронно), `/project`. |
| Управление | Нативные кнопки прежде команд (4.3.0): действие живёт под сообщением, к которому относится; карточка темы = статус + настройки с перерисовкой на месте; меню «/» — 4 команды; текстовые команды остаются запасным входом. |
| Rewind | `/rewind` (список чекпойнтов хода кнопками → `--rewind-files`) — за флагом `FILE_CHECKPOINTING`, поздняя фаза. |
| Доступ | `ALLOWED_USERS` обязателен; `ALLOWED_CHATS`; чужие игнорируются молча; `NOTIFY_CHAT`. Ролей нет. |
| Доставка | Outbox в Postgres, at-least-once, шлюз на тему, 429 → пауза шлюза, дедуп `update_id`. |
| Деплой | docker-compose: `bot` (python + node + `claude`, non-root), `db` (postgres + миграции). Секреты в `settings_local.py`/`.env`. |
| Тесты | По CLAUDE.md §2: e2e через реальный aiogram Dispatcher + recording-сессия + **fake `claude`** (скрипт, играющий сценарий stream-json) + реальный Postgres; unit — сплиттер, прогресс, батчер, парсер stream-json. |
| Язык | Тексты бота — русский (как референсы); имена команд — английские. Локализация — не в scope. |

## 4. UX-спецификация

### 4.1 Доступ и безопасность

- **`ALLOWED_USERS`** — кто управляет ботом. Список Telegram id, обязателен, не пустой.
  Сообщение или callback от чужого — **молча** игнорируется (без typing, без ответа);
  id/username пишутся в лог. На callback чужой получает тост «Not authorized».
- **`ALLOWED_CHATS`** — где бот вообще говорит. Пусто (по умолчанию) — везде, откуда пишет
  разрешённый пользователь. Смысл: бота можно добавить в чужую группу, а ответ (пути,
  вывод команд) прочитают все.
- Токен бота **не попадает в окружение** дочерних процессов (`claude`, MCP-сервер, STT/TTS)
  и вырезается из текстов ошибок. Модель, выполняющая shell, не может прочитать его.
- MCP-сервер `tgbridge` общается с демоном по unix-сокету с правами `0600`; сокет несёт
  идентификатор темы, выданный демоном при запуске процесса (env `TGBRIDGE_TOPIC_TOKEN`),
  чужой процесс не может ответить за чужой запрос.
- `NOTIFY_CHAT` (`chat_id` или `chat_id:thread_id`): при старте
  `🌅 Я на месте. Бот @имя, режим <perm>, тем: N, версия X`, при остановке `⏹ Останавливаюсь.`
  с числом прерванных ходов.
- В тему приходят только сообщения из этой темы; модель видит только их (плюс transcript
  сессии). Об этом сказано в преамбуле.

### 4.2 Темы и сессии

| Где пишут боту | Сколько сессий | Drafts | `/project` |
|---|---|---|---|
| Личный чат с включёнными topics (рекомендуется) | По одной на тему; General topic — тоже тема | да | да |
| Личный чат без topics | Одна на чат | да | нет |
| Форум-супергруппа с Topics | По одной на тему; General — тоже | нет (edit-in-place) | да (право «Управление темами») |
| Группа без Topics | Одна на чат | нет | нет |

**Создание темы (записи).** Первое обычное сообщение или любая команда, кроме справочных
(`/help`, `/whoami`, `/topics`, `/cancel`), создаёт запись темы: новый session id
(uuid4), директория `DEFAULT_CWD`, режим прав, модель и усилие из конфига, название темы (из
Telegram, если известно). Процесс `claude` поднимается при первом ходе.

**Тема, созданная пользователем в личке** (`ForumTopicCreated` с `is_name_implicit`): бот
после первого хода переименовывает её по сгенерированному заголовку сессии Claude Code
(первые 40 символов), если пользователь не назвал сам.

**`/project [алиас | путь]`** — создать новую тему под проект и привязать к директории.
Имя темы = алиас или последний компонент пути; цвет иконки — по хэшу имени (стабильный).
В новой теме: `📁 <путь>` / `Тема готова, контекст чистый. Пиши сюда.`; в исходной —
`✅ Тема <имя> открыта.` Без аргумента — справка и список алиасов. Ошибки: нет директории
(`⚠️ нет такой директории`), не форум / нет права — понятное сообщение с причиной.

**`/topics`** — список тем демона: `<имя> — <директория> — <статус процесса>` или `Пока пусто.`

**`/status`** — мгновенно, даже посреди хода:

```
Тема         <имя> (chat_id:thread_id)
Сессия       <session id> · <заголовок сессии>
Директория   <путь>
Модель       <имя | по умолчанию>   Усилие  <effort | по умолчанию>
Права        <режим> (только эта тема)   Правил: N
Характер     <путь | нет>   Голос <вкл|выкл>
Процесс      живой, 12 м · спит
Ход          идёт 1 м 12 с · Grep → Read src/main.rs · нет
Staging      2 форварда, 1 файл
Последний    1 м 12 с · $0.08 · 3 шага · 12k in / 1.4k out
Лимиты       5 ч: 25% (сброс через 2 ч 50 м) · 7 дн: 10%
```

Строка «Лимиты» — из последнего `rate_limit_event` любой темы (загрузка окон подписки);
на API-ключе строки нет.

### 4.3 Команды

Правила: команда — первое слово с `/`; суффикс `@bot` отбрасывается; регистр не важен;
остаток — аргумент; команда может быть подписью к медиа. **Любая неизвестная демону
`/команда` уходит в Claude Code как ход** (так работают `/compact`, `/context`, `/cost`,
`/doctor`, skills). Исключение: `/clear` перехватывается и равен `/new`.

Обозначения эффекта: **контекст остаётся** — процесс перезапускается с `--resume`;
**контекст заново** — новый session id.

| Команда | Действие | Эффект | Ответ |
|---|---|---|---|
| `/new` (`/clear`) | Новый контекст в теме | заново | `🆕 Новый контекст. Прошлая сессия сохранена — /sessions.` |
| `/stop` | Погасить процесс, контекст сохранить | остаётся | `⏸ Процесс остановлен, контекст сохранён.` |
| `/cancel` | Прервать текущий ход (вне очереди темы) | остаётся | draft/прогресс → `🛑 Прервано.`; иначе `Нечего прерывать.` |
| `/retry` | Повторить последний ход (хранится в БД) | — | ход; или `Нечего повторять.` |
| `/status` | Состояние темы | — | см. 4.2 |
| `/cd <путь>` | Сменить директорию (`~` раскрывается, только внутри `WORK_ROOT`) | заново | `📁 <путь>` / `Контекст начат заново — сессия привязана к директории.` |
| `/go [алиас]` | `/cd` по алиасу из `PROJECTS`; без аргумента — список | заново | `Куда идём:` + список |
| `/project [алиас\|путь]` | Новая тема под проект | новая тема | см. 4.2 |

| `/resume <id\|prefix≥4\|name>` | Подключить сессию; тема переезжает в её директорию | подмена | `🔗 Подключилась к сессии <id>` / `Директория: <путь>` / предупреждение про открытый терминал |
| `/branch [имя]` | Fork текущей сессии в **новую тему** (`--fork-session`, `--name`) | новая тема с копией | в исходной `🌿 Ветка <имя> открыта.`, в новой `Продолжаю с копии контекста.` |
| `/rename <имя>` | Имя сессии (уходит `/rename` в Claude Code) и имя темы | остаётся | `✏️ <имя>` |
| `/model [имя\|default]` | Модель темы; без аргумента — текущая | остаётся | `🤖 Модель: <имя>` |
| `/effort [low\|medium\|high\|xhigh\|max\|default]` | Усилие темы | остаётся | `🎚 Усилие: <x>` |

| `/soul [путь\|off\|default]` | Персона темы | остаётся | `🎭 Характер: <…>` |

| `/settings` | Inline-меню настроек (см. 4.9) | — | меню |

| `/files` | Последние файлы inbox темы | — | список |
| `/help`, `/whoami` | Справка; `Твой id / Чат / Тема` | — | текст |

#### 4.3.0 Кнопки вместо команд

Слеш-команды — запасной текстовый вход. Основной интерфейс управления — нативные кнопки
Telegram, привязанные к тому сообщению, к которому относится действие:

| Поверхность | Кнопки |
|---|---|
| Живой индикатор хода (draft / сообщение-прогресс) | `🛑 Прервать` (в личке — нативная кнопка Stop у draft'а) |
| Хинт `🕐 Дописываю текущий ход` | `🛑 Прервать текущий` |
| Вердикт `🛑 Прервано.`, `💥 Процесс упал`, `⏱ Таймаут` | `🔁 Повторить` |
| Вердикт `🔒 Отклонено без спроса: …` | `🔓 Разрешать правки` (тема → `acceptEdits`), `🔁 Повторить` |
| Вердикт `⏹ Достигнут лимит …` | `▶️ Продолжить` (ход с текстом «продолжай») |
| **Карточка темы** (`/status`) | ряды: `🆕 Новый контекст` `⏸ Стоп процесса` · `🔐 Права: prompt` `🤖 Модель: …` `🎚 Усилие: …` · `📁 Проект…` `🧹 Сжать` · `🔄 Обновить` `✖ Скрыть`; пока идёт ход — первый ряд `🛑 Прервать`. Нажатие переключает и перерисовывает карточку на месте |
| Списки сессий, проектов, чекпойнтов | строки-кнопки (4.3.1, фазы 6 и 8) |
| Карточки разрешений, вопросов, планов | 4.6, 4.7 |

Кнопка и команда вызывают одну и ту же функцию. `callback_data` = `<действие>:<topic_id>[:<аргумент>]`
(≤ 64 байта); кнопка устаревшего сообщения (тема удалена, запрос закрыт, демон перезапущен)
отвечает тостом «Уже неактуально». Reply-клавиатура не используется: она не привязана к теме и
оставляет сообщение в ленте на каждое нажатие.

В меню «/» Telegram регистрируются только команды без естественной поверхности: `status`
(открыть карточку темы), `new`, `project`, `help`. Остальные (`cancel`, `retry`, `stop`, `cd`,
`go`, `sessions`, `resume`, `branch`, `model`, `perm`, `effort`, `soul`, `voice`, `usage`,
`topics`, `whoami`, `compact`) работают текстом, но в меню не показываются.

#### 4.3.1 Карточка `/sessions`

```
Сессии в ~/src/app:
▸ 3f2a9c1d · 5 мин назад · «Починить flaky-тест auth» · терминал
▸ 8b77e0aa · 2 ч назад · «Миграция на aiogram 3.31» · эта тема
▸ …
```

Каждая строка — кнопка `🔗 3f2a9c1d` (= `/resume 3f2a9c1d`) и `🌿` (= `/branch` из
неё). Пометка «эта тема» / «тема <имя>» / «терминал» по тому, знает ли демон эту сессию.
Если пусто: `В <директория> сессий пока нет.`

### 4.4 Входной конвейер

#### 4.4.1 Батчер

- Принимаются: text, photo, document, voice, audio, video_note, video (только caption),
  forward любого из них, edited_message, callback_query, stopped_message_generation.
  Стикеры, геолокация, контакты, опросы — игнорируются (подпись, если есть, уходит текстом).
- Ключ батча — **тема** `(chat_id, thread_id)`. Скользящее окно `BATCH_WINDOW_MS = 300`:
  первое сообщение запускает таймер, каждое следующее сбрасывает. Так альбом, серия
  форвардов, «текст + фото + голос» становятся одним ходом без разбора `media_group_id`.
- Батч сортируется по `message_id`; **якорь** — первое сообщение (из него reply-цель и
  цитата).
- **Сериализация**: ходы темы строго по очереди. Сообщение во время хода — следующий батч;
  один раз на ход в тему приходит `🕐 Дописываю текущий ход — это следующим.` Очередь темы
  ≤ 32 батчей; при переполнении — `⚠️ Очередь полна, повтори позже.`, сообщение не теряется
  молча.
- Команды демона **не попадают в батч**: обрабатываются сразу (`/cancel`, `/status` — вне
  очереди; остальные — через очередь темы, чтобы `/cd` не перебил идущий ход).

#### 4.4.2 Prompt или staging

| Сообщение | Настройка | Решение |
|---|---|---|
| Текст, фото (с подписью или без), видео с подписью | — | prompt |
| Forward текста/фото/документа | `forward_as_prompt` (off) | off → staging; on → prompt |
| Voice / audio / video_note | `voice_as_prompt` (on) | on → prompt; off → staging |
| Документ без подписи | — | staging (файл сохранён, реакция 👀) |
| Документ с подписью | — | prompt (подпись — вопрос) |
| Правка отправленного сообщения | — | prompt с пометкой `[правка предыдущего сообщения]`, в чат `✏️ Вижу правку — отвечаю на неё.` |

Батч — prompt, если хотя бы один элемент prompt. **Staging** темы — очередь элементов в
БД; при следующем prompt-ходе они уходят **в начале** того же хода в фиксированном порядке
(форварды → файлы → транскрипции), затем элементы батча. После хода staging пустеет. На
staging-элемент бот ставит реакцию 👀 (если `REACTIONS`), ничего не пишет. `/status`
показывает размер staging; `/new` очищает его.

#### 4.4.3 Как собирается текст хода

Порядок частей: цитата reply → staging → элементы батча строго по `message_id` (порядок отправки;
комментарий к форвардам Telegram шлёт первым, и он остаётся первым), каждый как:

| Отправлено | Что получает Claude Code |
|---|---|
| Текст | как есть |
| Фото | image block (base64, лучшее качество, ≤ 5 МБ после даунскейла до 1568 px) **и** `[фото сохранено: <inbox-путь>]`, чтобы модель могла Read/скопировать файл |
| Альбом | один ход: все фото и все подписи |
| Документ | сохранён в `<INBOX>/<topic>/<YYYYMMDD>/<sanitized-name>` (коллизии → `_1`, `_2`), в ход `[файл <имя>: <путь>] (<размер>)` |
| Голосовое / аудио / кружок | скачано; при `TRANSCRIBE_CMD` → текст, в чат эхо `🎤 _текст_` (≤300 символов, reply на голосовое); иначе `[голосовое: <путь>]` |
| Forward | `[переслано от <Имя Фамилия (@username) | Chat name "…">]` первой строкой, далее текст; фото форварда сохраняет image block |
| Reply на сообщение бота | `[в ответ на твой ответ: «…»]` (≤700 символов; если выделена цитата — она) |
| Reply на чужое/своё сообщение | `[в ответ на сообщение: «…»]`; корневое сообщение темы не цитируется |
| Подпись к медиа | текст сообщения, в т.ч. команды |

Пустой ход (стикер без подписи) отбрасывается. Файлы inbox чистятся через `INBOX_TTL_DAYS`.
Лимиты: файлы ≤ 20 МБ (`getFile`), голос ≤ 25 МБ; больше — reply `⚠️ Файл больше 20 МБ,
Telegram не отдаёт его ботам.`, элемент пропускается, вопрос не теряется.

#### 4.4.4 Квитанции реакциями (`REACTIONS = True`)

| Событие | Реакция бота на сообщение пользователя |
|---|---|
| Сообщение принято в staging | 👀 |
| Ход поставлен в очередь (тема занята) | 🕐 текстом (реакции такой нет), реакция 👀 |
| Ход начат | реакция снимается, начинается typing/draft |
| Ход завершился ошибкой | 👾 |

Реакции — единственная «тихая» обратная связь; они не заменяют текстовые вердикты.

### 4.5 Как приходит ответ

#### 4.5.1 Ход в чате

1. Сразу — `sendChatAction typing` (повторяется каждые 4 с, не дольше 180 с) с
   `message_thread_id`.
2. Через 1.5 с или при первом событии от модели появляется **живой индикатор**:
   - **личка** (`USE_DRAFTS`): `sendRichMessageDraft` c `draft_id = turn_id`, `can_stop=true`;
   - **группы/форумы**: сообщение-прогресс с inline-кнопкой `🛑 Прервать`, редактируется.
3. Готовые куски ответа приходят **rich-сообщениями** по естественным границам (4.5.4).
4. По завершении: draft исчезает сам при отправке финала; сообщение-прогресс удаляется
   **после** доставки финала.
5. Опционально: подпись со статистикой, голосовое.

#### 4.5.2 Живой draft (личка)

Содержимое draft — markdown:

```
<tg-thinking>копаю ⛏️ Grep → Read …/src/main.rs (4 · 1:12)
🧠 Похоже, тест падает из-за таймзоны в фикстуре…</tg-thinking>
<хвост текущего текстового сегмента, до 30 000 символов>
```

- Строка прогресса — как в claude-tg: **фраза** (случайная, один раз на диапазон времени:
  до 20 с «уже смотрю 👀» / «поехали 🚀»; до 2 мин «копаю ⛏️» / «вникаю 🤔»; дольше «завари
  чай, я ещё вожусь 🍵»), **след** — последние три инструмента через `→`, у текущего —
  одна деталь ≤ 60 символов (путь для Read/Edit/Write/NotebookEdit, команда для Bash,
  шаблон для Grep/Glob, описание для Task/Agent, URL для WebFetch, запрос для WebSearch;
  пути режутся спереди, команды сзади; для MCP и прочих — только имя: во входе может быть
  секрет), счётчик вызовов и время.
- Подагенты (`parent_tool_use_id ≠ null`): в следе показываются как `Task ▸ Grep`.
- **Размышления** (`THINKING_PREVIEW`): последняя непустая строка `thinking_delta`
  (≤300 символов) с 🧠; при коротких — `🧠 Думаю…`. В сохраняемый ответ размышления не
  попадают.
- **Текст**: показывается без последнего (возможно недописанного) слова, не раньше 50
  накопленных символов; одинаковое содержимое повторно не шлётся; при > 30 000 символов
  хвост замораживается с ` ⏳…` до финала.
- Draft живёт ~30 с, поэтому во время долгих tool call переотправляется каждые 20 с.
- Пейсинг: один **шлюз** на ход, trailing-edge, интервал `DRAFT_MIN_INTERVAL = 1.0 с`;
  429 закрывает шлюз на `retry_after`; последнее состояние всегда доезжает; перед финалом
  отложенные обновления отменяются.
- Если Telegram отверг draft (не личка, ошибка разметки) — ход продолжает в режиме
  сообщения-прогресса.

#### 4.5.3 Сообщение-прогресс (группы, форумы, fallback)

Обычное сообщение `<фраза> _<след>_ (<N> · <м:сс>)` + при `STREAM_PREVIEW` — хвост текста
(последние 600 символов) под чертой; кнопка `🛑 Прервать`. Перерисовка через шлюз
`EDIT_MIN_INTERVAL = 3.0 с` (правки тратят тот же лимит чата, что и ответы). Если правка
провалилась (сообщение удалили) — следующий апдейт создаёт новое.

#### 4.5.4 Доставка текста

- Текстовый сегмент уходит финальным rich-сообщением: по завершении текстового блока
  (CLI присылает `assistant[text]` отдельным событием сразу после `content_block_stop`,
  до следующего tool call), при накоплении 30 000 символов, в конце хода. Сегменты короче
  `MIN_SEGMENT_CHARS = 120` перед tool call не отправляются отдельно, а склеиваются со
  следующим сегментом (чтобы «Посмотрю файл.» не засорял ленту) — это отличие от claude-tg.
- Rich Markdown передаётся **как есть**: заголовки, таблицы, списки, code fences с языком,
  диффы (` ```diff `), формулы, `<details>` для длинного вывода. Никакого экранирования.
- Если Telegram отверг разметку (`can't parse`) — то же содержимое уходит `sendMessage`
  plain, порезанное по 4 000; ответ не теряется. Прочие ошибки — в outbox-повтор.
- Сплиттер: порог 30 000; точка разреза ищется назад по `\n\n`, `\n`, `. `, пробелу; блок
  кода закрывается в конце чанка и переоткрывается с тем же языком в начале следующего;
  таблица не режется посередине (разрез до неё).
- Ответ целиком длиннее `ANSWER_FILE_THRESHOLD = 50 000` символов — файлом `answer-<turn>.md`
  с подписью `Ответ целиком — в файле.` плюс первые 2 000 символов текстом.
- Бот отвечает reply'ем только если якорное сообщение само было reply; иначе обычным
  сообщением (лента без лишних цитат). В темах reply не нужен — тема и есть контекст.
- Каждый отправленный чанк запоминается в `message_links` (для цитат в reply и `/rewind`).

#### 4.5.5 Сообщения в конце хода

| Ситуация | Сообщение |
|---|---|
| Ход завершён без текста (только инструменты, `/compact`) | `✔️ Готово — в ответе не было ни слова текста.` (для `/compact` — `🧹 Контекст сжат: <pre_tokens> → компакт.`) |
| `result.is_error` | `⚠️ Ход завершился с ошибкой: <result>` |
| `result.subtype = error_max_turns / error_max_budget_usd` | `⏹ Достигнут лимит <ходов|бюджета>. Контекст цел — продолжай или /retry.` |
| `permission_denials` не пусто | `🔒 Отклонено без спроса: Bash(rm -rf …), WebFetch` + совет `/perm prompt` |
| `SHOW_TURN_STATS` | курсив `1 м 12 с · $0.08 · 3 шага · 12k/1.4k` (цена — если CLI сообщил) |
| `system/api_retry` дольше 10 с | в индикатор `⏳ API: повтор 2/10 (rate_limit)` |

#### 4.5.6 Обрыв хода

| Причина | Вердикт (заменяет индикатор, кнопка убирается) |
|---|---|
| `/cancel`, кнопка 🛑, `stopped_message_generation` | `🛑 Прервано.` Мост шлёт SIGINT; CLI дописывает в транскрипт `[Request interrupted by user]`, отдаёт `result/error_during_execution` и выходит; накопленный текст сегмента отправляется финалом с пометкой `(прервано)`. Следующий ход — `--resume` |
| `TURN_TIMEOUT_SECS` (60 мин) | `⏱ Ход шёл дольше лимита и был прерван. Контекст сохранён.` |
| Процесс упал (после одной незаметной попытки повтора) | `💥 Процесс claude завершился (код N).` + хвост stderr (без токенов) + `Контекст сохранён — /retry повторит.` |
| Демон остановлен | `⏹ Демон остановлен посреди хода. Контекст цел — /retry повторит.` |

Во всех случаях контекст сохраняется; под вердиктом — кнопка `🔁 Повторить` (= `/retry`).

#### 4.5.7 Гарантии доставки

Все исходящие вызовы (rich, plain, файлы, голос, правки, реакции, удаления) сначала пишутся
в `outbox` и снимаются после подтверждения Telegram. Недоставленное из-за падения демона
уезжает при старте (at-least-once). Один воркер на тему; 429 → пауза только этой темы.
Сообщение, застрявшее дольше 10 минут, помечается failed с записью в лог и в тему уходит
`⚠️ Часть ответа не доставлена.` Draft-обновления в outbox **не** пишутся (эфемерны).
Входящие `update_id` дедуплицируются в БД (повтор = повторный shell).

### 4.6 Разрешения

#### 4.6.1 Режимы темы

`DEFAULT_PERMISSION_MODE` обязателен в конфиге. `/perm <режим>` переопределяет для темы;
смена перезапускает процесс, контекст остаётся.

| Режим моста | Что передаётся Claude Code | Поведение |
|---|---|---|
| `prompt` (рекомендуется) | `default` + prompt tool | Всё, что Claude Code не решил сам по правилам, приходит кнопками |
| `acceptEdits` | `acceptEdits` + prompt tool | Правки и файловые команды проходят сами, остальное — кнопками |
| `plan` | `plan` + prompt tool | Только чтение; план — карточкой (4.7.2) |
| `auto` | `auto` + prompt tool | Классификатор Claude Code; спорное — кнопками (если CLI доводит до prompt tool) |
| `dontAsk` | `dontAsk` | Всё, что потребовало бы вопроса, отклоняется; список в конце хода |
| `bypass` | `bypassPermissions` | Проверок нет. Полный shell с телефона. Требует `ALLOW_BYPASS = True` в конфиге |

Отклонения без вопроса всегда перечисляются в конце хода (4.5.5), чтобы отказ не выглядел
как «бот сломался».

#### 4.6.2 Карточка запроса

```
🔐 Bash просит разрешение
```bash
cargo test --workspace
```
_Проверить, что тесты проходят после правки_   ← description, если есть
```

Кнопки: строка 1 `✅ Разрешить` `❌ Отклонить`; строка 2 `🔓 Всегда: Bash(cargo test *)`
(до двух кнопок — из `permission_suggestions`); строка 3 `✏️ Отклонить и объяснить`
(следующее текстовое сообщение темы становится `message` отказа — модель получает
подсказку, что делать вместо этого).

Рендер входа по инструменту:

| Инструмент | Что показано |
|---|---|
| `Bash` | команда в ` ```bash `, `description` курсивом |
| `Edit` | путь + ` ```diff ` из `old_string`/`new_string` (≤ 60 строк, дальше `…`) |
| `Write` | путь, размер, первые 40 строк содержимого в ` ``` ` с языком по расширению; если файл существует — diff |
| `NotebookEdit` | путь + ячейка + diff |
| `Read`/`Grep`/`Glob` | путь/шаблон одной строкой |
| `WebFetch`/`WebSearch` | URL / запрос |
| `AskUserQuestion`, `ExitPlanMode` | не карточка разрешения, см. 4.7 |
| MCP и прочие | имя инструмента и вход в ` ```json ` ≤ 700 символов, ключи с `token|secret|password|key` маскируются |

Хвост карточки после нажатия: кнопки убираются, дописывается `✅ разрешено` /
`❌ отказано` / `❌ отказано: «<текст>»` / `🔓 разрешено, и больше не спрошу: <правило>`.
Кнопка от устаревшего запроса (после перезапуска) — тост «Запрос уже неактуален».
Без ответа `PERMISSION_TIMEOUT_SECS` (10 мин) — отказ с текстом причины. Если демон
недоступен, MCP-сервер сам отвечает отказом через 15 с: зависания навсегда не бывает.

Пока висит запрос, индикатор показывает `🔐 жду разрешения (Bash)`; typing не шлётся.

#### 4.6.3 «Всегда»

- CLI не передаёт в prompt tool подсказок правил, поэтому правило строит мост:

  | Инструмент | Правило кнопки «Всегда» |
  |---|---|
  | `Read`, `Grep`, `Glob`, `WebSearch`, `NotebookRead`, `TodoWrite`, `TaskCreate/Update/List` | имя инструмента целиком |
  | `Bash` | префикс `Bash(<cmd> <subcmd> *)` для известных программ с подкомандами (`git`, `npm`, `cargo`, `docker`, `make`, `pytest`, `uv`, `pip`…), иначе точная команда `Bash(<команда>)`; кнопки нет для многострочных, длиннее 120 символов, с `&&`/`|`/`;`, и для `rm`, `sudo`, `curl`, `wget` |
  | `WebFetch` | `WebFetch(domain:<host>)` |
  | `mcp__<server>__<tool>` | имя инструмента целиком, кроме `mcp__tgbridge__*` |
  | `Edit`, `Write`, `NotebookEdit` | кнопки нет — ответ на «хочу, чтобы правки проходили сами» это осознанный `/perm acceptEdits` |

- Ответ содержит `updatedPermissions: [{type: addRules, behavior: allow, destination:
  localSettings, rules: [{toolName, ruleContent}]}]`: Claude Code сам пишет правило в
  `.claude/settings.local.json` в корне репозитория проекта (spike 1), оно действует в
  терминале и переживает перезапуск процесса. Мост дублирует запись в `topic_rules`
  (тема, правило, путь файла) для учёта.
- `/perm` показывает правила, добавленные ботом, и остальные allow-правила из
  `settings.local.json` (только чтение); `/perm forget` удаляет из файла правила, которые
  добавил бот в этой теме: `Забыла N правил. Снова буду спрашивать.`

#### 4.6.4 Правила поверх режима

Глобальные ключи конфига передаются напрямую: `ALLOWED_TOOLS`, `DISALLOWED_TOOLS`,
`CLAUDE_SETTINGS` (файл/JSON, в т.ч. hooks и `permissions.ask`), `ADD_DIRS`. Часть вызовов
Claude Code разрешает по своим правилам и до кнопок они не доходят: `prompt` = «спрашивать,
где положено», а не «кнопка на каждый чих».

### 4.7 Вопросы и планы

#### 4.7.1 AskUserQuestion

По одной карточке на вопрос, последовательно:

```
❓ Формат (1/2)
Как оформить вывод?
```
Кнопки: по варианту в строке — `Summary — краткий обзор`, `Detailed — с примерами`;
для `multiSelect` — тоггл `☐/☑` и кнопка `Готово`; последняя строка `✍ Свой ответ`
(следующее текстовое сообщение темы — ответ; `AWAITING_INPUT` в состоянии темы, таймаут
`QUESTION_TIMEOUT_SECS` 30 мин). После ответа карточка редактируется: `→ Summary`.
Когда отвечены все — `updatedInput = {questions, answers}`; при свободном тексте вне
структуры — `response`. Таймаут → deny с `message = "user did not answer"`. Индикатор:
`❓ жду ответа`.

#### 4.7.2 ExitPlanMode

Rich-карточка: заголовок `📋 План готов`, полный markdown плана (сплиттер при длине),
кнопки на последнем чанке: `✅ Выполнять (правки без вопросов)` → allow +
`setMode acceptEdits`; `✅ Выполнять, спрашивать про правки` → allow + `setMode default`;
`✏️ Доработать` → deny с `message` = следующее текстовое сообщение темы (`AWAITING_INPUT`).
Если `setMode` через prompt tool не сработает (эксперимент 2), мост меняет режим темы и
перезапускает процесс после хода — пользователь разницы не видит. Одобрение плана
переименовывает сессию и тему по заголовку плана (Claude Code делает это сам для сессии).

### 4.8 Файлы наружу, голос, персона

**`send_file`** (MCP-инструмент `mcp__tgbridge__send_file {path, caption?}`): демон
отправляет файл ≤ 50 МБ в тему (фото/видео — как медиа, остальное — документом, подпись
≤ 1024), инструмент возвращает модели `File <имя> (<размер>) sent`. Разрешается по
правилам Claude Code как любой MCP-инструмент (по умолчанию — кнопка; совет — «Всегда»).
Флаг `BRIDGE_SEND_FILE_TOOL` (on).

**Голосовой ввод**: `TRANSCRIBE_CMD` с плейсхолдерами `{file}` (OGG/Opus), `{wav}`; текст —
со stdout; лимит 3 мин. Пример — whisper-cli. Ошибка → в ход уходит путь к файлу.

**Голосовые ответы**: `/voice on` → одно голосовое на ход после всего текста; читается
только проза (код, разметка, таблицы выбрасываются), ≤ 900 символов по границе
предложения; `TTS_CMD` получает `{text_file}`, `{wav}`, `{out}` (OGG/Opus), лимит 2 мин.
Без `TTS_CMD`: `Синтез не настроен: задай TTS_CMD.`

**Персона (SOUL)**: `SOUL_PATH` (по умолчанию `~/.config/<app>/SOUL.md`, если есть),
`/soul <путь|off|default>`; уходит через `--append-system-prompt-file`. Преамбула моста
(`bridge_preamble.md` в репозитории, переопределяется `BRIDGE_PREAMBLE_PATH`) дописывается
всегда: канал — Telegram, тема — одна сессия, файлы пользователя лежат в `<inbox>`,
файлы наружу — через `send_file`, форматирование под чтение с телефона (заголовки и
таблицы допустимы, длинный вывод — в файл), вопросы — через AskUserQuestion. Файлы
читаются при запуске процесса: правка вступает в силу после `/stop` или простоя.

### 4.9 Карточка темы, настройки и расход

**Карточка темы** (`/status`) объединяет статус и настройки: текст из 4.2 плюс inline-кнопки
из 4.3.0. Нажатие переключает значение и перерисовывает карточку на месте
(`editMessageText`); `🔄 Обновить` перечитывает состояние; `✖ Скрыть` удаляет карточку.
Переключатели прав, модели и усилия — циклические (`🔐 Права: prompt` → `acceptEdits` → `plan`
→ …; `bypass` только при `ALLOW_BYPASS`). Пользовательские флаги ниже — в ряду `⚙️ Ещё`,
раскрывающем вторую страницу карточки.

| Настройка | Область | Кнопка | Дефолт |
|---|---|---|---|
| `stream_preview` | тема | `Превью ответа: вкл` | `STREAM_PREVIEW` |
| `thinking_preview` | тема | `Размышления: вкл` | `THINKING_PREVIEW` |
| `show_turn_stats` | тема | `Статистика хода: выкл` | `SHOW_TURN_STATS` |
| `voice` | тема | `Голосом: выкл` | off |
| `voice_as_prompt` | пользователь | `Голос = вопрос: вкл` | on |
| `forward_as_prompt` | пользователь | `Форвард = вопрос: выкл` | off |
| `reactions` | пользователь | `Реакции: вкл` | `REACTIONS` |
| `verbose_tools` | тема | `Вывод инструментов: выкл` | `VERBOSE_TOOL_OUTPUT` — результаты tool call отдельным plain-сообщением ≤ 4 000 в `<details>` |
| `model`, `effort`, `perm` | тема | циклический выбор `Модель: <sonnet>` | из конфига |

**`/usage`** — карточка за календарный месяц: по темам (`<тема>: N ходов, $X, in/out`), по
моделям, итог; кнопка `Скрыть`. Источник — `result.usage` и `total_cost_usd` (если есть;
на подписке цены нет — показываем токены).

### 6.3 Командная строка `claude`

```
claude -p --verbose
       --input-format stream-json --output-format stream-json
       --include-partial-messages --replay-user-messages
       --permission-mode <default|acceptEdits|plan|auto|dontAsk|bypassPermissions>
       --permission-prompt-tool mcp__tgbridge__approve        # все режимы, кроме dontAsk/bypass
       --mcp-config '{"mcpServers":{"tgbridge":{"command":"python","args":["-m","app.bridge.mcp_server"],"env":{"TGBRIDGE_SOCKET":"…","TGBRIDGE_TOPIC_TOKEN":"…"}}}}'
       --session-id <uuid>            # первый запуск темы
       --resume <uuid> [--fork-session --name <имя>]   # последующие / branch
       [--model …] [--effort …] [--fallback-model …] [--max-budget-usd …]
       --append-system-prompt-file bridge_preamble.md [--append-system-prompt-file SOUL.md]
       [--settings …] [--add-dir …] [--allowed-tools …] [--disallowed-tools …]
       [--forward-subagent-text]
```

`--verbose` обязателен для stream-json. Парсер обрабатывает: `system/init`,
`system/compact_boundary`, `system/permission_denied`, `system/api_retry`, `assistant`
(по одному блоку: `thinking` — игнор, `text` — сегмент, `tool_use` — след), `user`
(`tool_result` — verbose-режим), `stream_event` (`text_delta`, `thinking_delta`,
`content_block_start:tool_use`), `result`, `rate_limit_event` (для `/status`); остальные
(`system/status`, `system/thinking_tokens`, неизвестные типы) — игнорирует без ошибки.

Рабочая директория — директория темы. Окружение: `CLAUDE_CONFIG_DIR`, `HOME`, `PATH`,
`CLAUDE_CODE_ENABLE_SDK_FILE_CHECKPOINTING` (при флаге), провайдерские ключи из `.env`;
токен бота и `DATABASE_URL` **вырезаны**. Ход = одна строка stdin
`{"type":"user","message":{"role":"user","content":[…]}}`; ход завершается **только** по
`result`.

### 6.4 Жизненный цикл процесса

- **Тёплый процесс**: поднимается при первом ходе, обслуживает ходы подряд. Простой
  `IDLE_TIMEOUT_SECS` (30 мин) → stdin закрывается, процессу дают 10 с выйти, затем SIGTERM.
  Следующий ход поднимает `--resume`.
- **Что перезапускает процесс, сохраняя контекст**: `/stop`, `/model`, `/effort`, `/perm`,
  `/soul`, простой, падение, прерывание (SIGINT завершает и ход, и процесс — spike 4),
  остановка демона, смена `ADD_DIRS`.
- **Что начинает контекст заново**: `/new`, `/clear`, `/cd`, `/go`, `/project`; `/resume`
  и `/branch` подменяют.
- **Session id**: если `system/init` или `result` сообщают id, отличный от ожидаемого
  (после `/compact`, `/clear` в процессе), тема принимает новый.
- **Падение**: ход повторяется один раз незаметно; повторное падение — `💥` + stderr-хвост.
  Если CLI говорит, что session id занят — тема переключается на `--resume`.
- **Лимит хода** `TURN_TIMEOUT_SECS` (60 мин) → отмена как по кнопке.
- **Остановка демона** (SIGTERM/SIGINT): идущие ходы прерываются с вердиктом, процессам —
  10 с на выход, outbox досылается, `NOTIFY_CHAT` получает `⏹`. После рестарта: темы,
  session id, настройки, правила, staging, очередь outbox и последний ход — в БД; кнопки
  старых карточек отвечают «Запрос уже неактуален».

### 6.5 Протокол MCP-сервер ↔ демон

`mcp_server.py` — минимальный stdio MCP-сервер (JSON-RPC 2.0, `initialize`, `tools/list`,
`tools/call`), без внешних зависимостей помимо стандартной библиотеки. На `tools/call`
открывает unix-сокет, шлёт одну JSON-строку `{token, tool, tool_use_id, args}` и ждёт
одну строку ответа. `approve` возвращает текст-контент со строкой JSON
`{"behavior": …}`; `send_file` — текст подтверждения. Таймаут ожидания демона по сокету
= `PERMISSION_TIMEOUT_SECS + 30`; при обрыве — deny с причиной. Демон по `token` находит
тему, создаёт `pending_prompt`, отправляет карточку и ждёт callback/текст/таймаут.

### 6.7 Тестовая инфраструктура (кратко; подробно — `specs/E2E_TESTS.md` в фазе 1)

  полученное со stdin в файл — тест ассертит, что ушло в Claude Code. Пустая очередь —

- **Тайминги**: окно батчера, шлюзы, idle/turn таймауты — патчатся в фикстуре приложения.

## 10. Manual smoke checklist (после деплоя)

1. `docker compose up -d --build`; в `NOTIFY_CHAT` пришло `🌅`.
2. В личке с topics: `/project <alias>` создаёт тему; в ней «что в этой директории?» — draft
   с `<tg-thinking>`, затем rich-ответ со списком; `/status` показывает сессию.
3. Reply на ответ бота с уточнением — в ходе есть цитата.
4. Альбом из 2 фото с подписью — один ход, модель видит оба изображения.
5. Форвард 3 сообщений без вопроса — реакции 👀, ответа нет; затем «о чём это?» — ответ
   учитывает все три.
6. Просьба поправить файл в `prompt`-режиме — карточка с diff; ✅ → правка применена;
   «Всегда» для `git status` → правило появилось в `.claude/settings.local.json`.
7. `/perm plan` + задача — карточка плана; «Выполнять» → правки идут в `acceptEdits`.
8. Модель задаёт вопрос (`AskUserQuestion`) — кнопки работают, «свой ответ» работает.
9. Кнопка Stop нативного draft'а прерывает ход; `/retry` повторяет.
10. Открыть сессию в терминале `claude --resume <id>` после `/stop` — контекст на месте;
    обратно `/resume <id>` из темы.
11. `/branch` создаёт тему с копией контекста.
12. Голосовое → эхо 🎤 и ответ; `/voice on` → голосовое в ответе.
13. `docker compose restart bot` посреди хода — вердикт `⏹`, `/retry` работает, кнопки
    старой карточки отвечают «неактуален».
14. В форум-супергруппе: то же без draft (прогресс редактируется), `/project` с правом тем.
