# Reference spec: нативный UX работы с LLM в Telegram-чате

Документ описывает **поведение** этого бота с точки зрения пользователя и транспорта: что происходит с каждым типом сообщения, как доставляется ответ, как история диалога ложится на чат. Цель — извлечь идеи и повторить их в другом проекте, поэтому описание не привязано к языку, фреймворку или базе данных: только поведение, правила, параметры и мотивация.

Как читать: разделы 1–9 — базовый чат-UX (обязательная часть), 10 — режим агента, 11–12 — команды, меню, роли, 13 — сводная таблица параметров, 14 — чек-лист переноса. Термины Telegram и LLM (reply, forward, draft, tool call, caption) оставлены английскими.

---

## 0. Принципы

Весь UX держится на пяти идеях. Остальное — следствия.

1. **Чат — это и есть интерфейс.** Нет состояний, визардов и «режимов ввода». Смысл действия определяется нативным жестом Telegram: reply — «продолжай эту ветку», forward — «положи это в контекст», голосовое — «это текст», документ — «положи файл в рабочее пространство», кнопка Stop — «хватит».
2. **Единица работы — батч, а не сообщение.** Всё, что пользователь отправил в течение короткого окна (альбом, несколько форвардов, текст + фото + голос), обрабатывается как один ход и получает один ответ.
3. **«Ответить» и «просто запомнить» — разные вещи.** Часть сообщений (форварды, документы без подписи, при желании голосовые) молча ложится в контекст без вызова модели. Пользователь сначала «скармливает» материал, потом задаёт вопрос.
4. **Каждое сообщение чата привязано к узлу истории.** Ответы модели, транскрипции, подтверждения загрузки, сгенерированные картинки, отправленные файлы — у всего есть id сообщения Telegram, по которому находится узел истории. Поэтому reply на что угодно продолжает именно ту ветку, а история диалога — дерево, а не список.
5. **Транспорт отвечает за доставку, рантайм — за модель.** Рантайм отдаёт поток событий (дельта текста, финальный ответ, начало/конец tool call) и получает функцию «отменено?». Транспорт решает, как это показывать, и сам сохраняет ответ ассистента в историю, потому что только он знает id отправленного сообщения.

## 1. Входной конвейер: батчинг и дебаунсер

### Поведение

- Бот принимает сообщения типов text, photo, voice, audio, video_note, document. Для video учитывается только caption (подпись), само видео игнорируется.
- Все входящие сообщения **одного пользователя** копятся в батч. Ключ батча — пользователь, а не чат: если пользователь пишет боту в двух чатах в пределах окна, сообщения попадут в один батч и будут обработаны в чате первого из них. На практике это не мешает, но при переносе стоит осознанно выбрать ключ `(user, chat)`.
- **Скользящее окно 300 мс.** Первое сообщение запускает таймер; каждое следующее сбрасывает его на 300 мс. Когда таймер истёк, батч закрывается. Так альбом (media group), серия форвардов или «текст + фото + голосовое подряд» собираются в один батч без анализа `media_group_id` — Telegram доставляет элементы альбома почти одновременно.
- Батч сортируется по `message_id`. Первое сообщение батча — **якорь**: из него берутся chat id, reply-цель для ответа и `reply_to_message` для выбора ветки истории (см. §7).
- **Сериализация ходов.** Батчи одного пользователя выполняются строго по очереди. Сообщение, пришедшее пока бот ещё отвечает, не теряется и не подмешивается в текущий ход — оно станет следующим батчем и обработается после завершения текущего.
- Из батча собирается один объект пользовательского ввода с четырьмя частями: текстовые элементы (текст + не более одной картинки на исходное сообщение), транскрипции голосовых, загруженные файлы и флаг `force_prompt` (см. §2).
- В контекст элементы укладываются **в фиксированном порядке**, независимо от порядка прихода: транскрипции → файлы → тексты/картинки. Каждый элемент — отдельное сообщение истории со своим id сообщения Telegram.

### Индикация

- На время обработки батча (транскрипция, вызов модели, tool calls) в чате показывается «печатает…» (`sendChatAction`), повторяемый каждые 2 с, не дольше 180 с.
- Тип действия зависит от операции: `typing` по умолчанию, `upload_document` при сохранении документа, `record_voice` при генерации голоса.

### Схема

```
сообщения пользователя ──► батч (окно 300 мс, сброс при каждом новом)
                              │
                              ▼
                     сортировка по message_id
                              │
        ┌─────────────────────┼─────────────────────┐
        ▼                     ▼                     ▼
   voice/audio/           photo/text            document
   video_note        (caption = текст)     (agent mode: в workspace,
   → транскрипция                          подтверждение + алиас)
        └─────────────────────┼─────────────────────┘
                              ▼
                 «батч — prompt?» (§2)
                    │нет            │да
                    ▼               ▼
            записать в          «печатает…» + ход модели
            контекст, молчать   → стриминг ответа (§9)
```

## 2. Prompt или контекст: матрица решений

Каждое сообщение батча классифицируется: **prompt** (нужен ответ) или **context-only** (сохранить в историю и промолчать). **Батч считается prompt, если хотя бы один его элемент — prompt.** Всё содержимое батча при этом попадает в контекст в любом случае.

| Сообщение | Настройка пользователя | Решение |
|---|---|---|
| Текст, фото (с подписью или без) | — | всегда prompt |
| Forward (текст, фото) | `forward_as_prompt` (по умолчанию **off**) | off → context-only; on → prompt, как обычное сообщение |
| Voice / audio / video_note | `voice_as_prompt` (по умолчанию **on**) | on → prompt; off → context-only |
| Document без caption | — | context-only (файл сохраняется, ответа нет) |
| Document с caption | `forward_as_prompt` для пересланных | prompt через `force_prompt`; **исключение**: пересланный документ при `forward_as_prompt=off` — caption считается исходным текстом, не вопросом → context-only |
| Video | — | только caption, prompt |

- `force_prompt` — подсказка транспорта рантайму: «батч не выглядит как вопрос, но в нём есть авторский текст, требующий ответа». Единственный источник сегодня — caption на документе. Флаг срабатывает только если во вводе есть содержимое.
- Context-only путь: элементы записываются в текущую ветку истории (ветка выбирается по тем же правилам, что и для prompt, §7), модель не вызывается, бот ничего не отвечает.
- Целевой сценарий: переслать боту пять сообщений из другого чата, затем написать «что они имели в виду?» — модель видит все пять с атрибуцией авторов.
- Проверочный кейс: альбом из нескольких документов, caption только у первого → один батч, один ответ, все файлы в контексте.

## 3. Форварды

- Сообщение считается пересланным, если у него есть `forward_origin` (Bot API 7+) или любое из legacy-полей `forward_from`, `forward_from_chat`, `forward_sender_name`.
- В контекст forward попадает **с атрибуцией автора** в первой строке, дальше с новой строки — текст форварда:
  - обычный пользователь → `Имя Фамилия (@username):` (если чего-то нет — только имя или только `@username`);
  - скрытый пользователь → его отображаемое имя;
  - чат или канал → `Chat name "<название>":`;
  - без текста (например, только фото) → строка с автором и двоеточием.
- **Пересланное фото сохраняет картинку**: она прикрепляется к тому же элементу контекста, что и подпись/атрибуция.
- **Forward никогда не считается reply.** Даже если в пересланном сообщении есть `reply_to_message`, оно не ветвит историю; используется текущая ветка.
- При `forward_as_prompt=on` форвард обрабатывается как обычное сообщение — без префикса автора и с немедленным ответом.
- Настройка `forward_as_prompt` в этом проекте не выведена в меню (осознанно: режим «сначала скорми, потом спроси» оказался полезнее), но хранится на пользователе.

## 4. Голос, аудио, кружки

### Входящие

- Voice, audio и video_note обрабатываются одинаково. Лимит 25 МБ; при превышении — reply «Voice file is too big», и элемент пропускается.
- Файл скачивается, конвертируется в mp3 (ffmpeg; для кружков извлекается звуковая дорожка), длительность считается **до** транскрипции и сразу записывается в usage (тарифицируется посекундно). Транскрипция — speech-to-text модель с temperature 0.
- **Транскрипт эхом отправляется пользователю** как reply на его голосовое, обычным текстом, чанками по 4080 символов. Если Telegram отверг отправку — транскрипция всё равно уходит в контекст (с id −1).
- В контекст текст попадает с префиксом `speech2text:` на первой строке, каждый чанк — отдельным сообщением истории, привязанным к id своего эхо-сообщения.
- **Алиас голосового.** Id исходного голосового сообщения пользователя привязывается к **последнему** чанку транскрипта: только его ветка (предки + он сам) содержит все чанки. Поэтому reply и на своё голосовое, и на любой чанк эха продолжает нужную ветку.
- Ответ на голосовое приходит, если `voice_as_prompt=on` (по умолчанию). При off голосовое — способ «надиктовать в контекст».

### Исходящие (TTS)

- Голосом бот отвечает **только по явной команде** `/text2speech`: озвучивается сообщение, на которое команда является reply, иначе — последнее сообщение диалога. Если текста нет — «No text to generate speech».
- На время генерации — действие `record_voice`; голос берётся из настройки пользователя (`tts_voice`, по умолчанию `onyx`); стоимость по символам записывается в usage.
- Если Telegram запретил отправку голосовых (настройки приватности получателя), бот объясняет это текстом.

## 5. Картинки

- Из `photo[]` берётся самый большой размер. Одна картинка на сообщение Telegram; альбом превращается в несколько элементов контекста по одной картинке в каждом. Caption становится текстом того же элемента; фото без подписи — элемент только с картинкой.
- Если текущая модель не поддерживает vision, пользователь получает ошибку и ход не выполняется. (В этом проекте это сырой текст исключения; при переносе — понятное сообщение вида «модель X не умеет работать с картинками».)
- **Хранение как URL.** В истории картинка лежит не как байты, а как ссылка на собственный image-proxy: `{proxy_base}/{file_id}_{tokens}.jpg`. Прокси по `file_id` скачивает байты у Telegram и отдаёт их провайдеру модели. Мотивация: vision-API провайдеров не могут ходить на `api.telegram.org` с токеном бота, а хранить байты в истории дорого.
- **Токены в имени файла.** В URL закодирована оценка стоимости картинки в токенах, посчитанная по правилам провайдера (масштабирование до 2048/768, разбиение на тайлы 512×512, 170 токенов на тайл + 85). Подсчёт размера контекста читает это число из URL и не скачивает картинку. Счёт токенов всегда выполняется до конвертации в base64.
- Конвертация в base64 — только на момент запроса и только для провайдеров, которым это нужно (Anthropic, локальные OpenAI-совместимые модели); результат кэшируется в памяти.
- Картинки не протухают по времени: `file_id` живёт долго, старый URL в воскрешённой ветке по-прежнему разрешается. Картинка исчезает из контекста только вместе с суммаризацией (саммари текстовое).

## 6. Документы и файлы (режим агента)

### Входящие

- Документы принимаются только при включённом режиме агента и доступном sandbox. Иначе — reply «Documents are not supported», подпись при этом тоже не сохраняется.
- Лимит 20 МБ (ограничение скачивания через Bot API). Имя файла санитизируется: остаются буквы (включая кириллицу), цифры, `_`, `.`, `-`, остальное → `_`. Коллизия имён в рабочем пространстве → суффикс `name_1.ext`, `name_2.ext`, …
- Файл кладётся в корень персонального рабочего пространства пользователя. На время загрузки — действие `upload_document`.
- Пользователь получает reply-подтверждение `Saved to agent workspace: <имя>`.
- В контекст попадает **одно** сообщение истории: `[file uploaded to agent workspace] <имя> (<размер> bytes)` и, если была подпись, её текст с новой строки. Сообщение привязано к id документа пользователя, а id подтверждения бота записывается как **алиас** того же узла. Reply и на свой документ, и на подтверждение продолжает нужную ветку.
- Подпись делает батч prompt (через `force_prompt`) — «вот файл, сделай с ним то-то» отвечается сразу. Документ без подписи — только сохранение, без ответа.
- **Ошибка загрузки не теряет вопрос:** в контекст идёт `[failed to upload file to agent workspace] <имя> (<причина>)` плюс подпись, пользователю показывается текст ошибки, и, если подпись была, агент всё равно отвечает (зная о сбое).

### Исходящие

- У агента есть инструмент «отправить файл в чат»: файл (до 50 МБ) уходит как документ с caption ≤ 1024 символов, инструмент сообщает модели «File <имя> (<размер> bytes) sent to chat».
- Id отправленного документа привязывается к записи tool-response в истории, так что reply на файл продолжает ту же ветку.
- Аналогично для сгенерированных картинок: изображение отправляется как фото с подписью `Image generated from prompt: … / Revised prompt: …` (обрезка до 1024), а в историю записывается tool-response `Generated Image: <image.png>` с id этого фото.

### Рабочее пространство (контракт, не реализация)

- Изолированное per-user пространство; shell без сохранения состояния между вызовами (cwd и переменные окружения сбрасываются, модели об этом сказано в описании инструмента).
- Инструменты: выполнить команду (с таймаутом), прочитать/записать/отредактировать файл, отправить файл в чат. Вывод команд обрезается до 10 000 символов.
- В system prompt агенту сообщается: у него есть личное рабочее пространство, файлы пользователя лежат в его корне, отправлять файлы нужно через инструмент.

## 7. Ветвление по reply и жизненный цикл контекста

### Модель хранения

- История — не список и не «диалоги», а **дерево сообщений**. Каждая запись хранит: содержимое в формате провайдера, роль, время создания, время последней активации, **материализованный список всех предков** (`previous_message_ids`, упорядоченный), `chat_id` и `tg_message_id` (−1 — у сообщения нет видимого аналога в чате), тип (обычное / саммари / reset).
- Список предков — снимок всего контекста на момент записи. Восстановление ветки — один запрос «дай сообщения с этими id, отсортируй по времени». Ветвление бесплатно: два ответа на одно и то же сообщение получают одинаковых предков и расходятся дальше. Сущности «диалог» нет вовсе.
- Таблица алиасов: `(chat_id, tg_message_id) → запись истории`. Используется для сообщений чата, у которых нет своей записи (подтверждение загрузки, голосовое пользователя за транскрипцией).

### Выбор контекста для нового батча (по приоритету)

1. **Явный снимок ветки** — используется только отложенными задачами агента (§10).
2. **Reply** (у якорного сообщения есть `reply_to_message`, и оно не forward): узел ищется по `(chat_id, reply_to_message_id)` сначала среди записей, затем среди алиасов. Контекст = предки узла + сам узел. **Окно устаревания не применяется:** reply на сообщение трёхнедельной давности воскрешает ветку.
3. **Без reply**: берётся последнее сообщение в паре (пользователь, чат). Если его время активации старше `MESSAGE_EXPIRATION_WINDOW` (1 час), контекст пустой — начинается новый разговор.
4. Если узла нет или это маркер `/reset` — пустой контекст.

### Ключевой приём: воскрешение ветки

При reply у **всех сообщений выбранной ветки** обновляется время активации. Значит, после одного reply на старое сообщение можно продолжать писать без reply — эта ветка становится «живой» по правилу 3. Пользователь ощущает это как «ткнул в старый ответ — вернулся в тот разговор».

### `/reset`

- Записывает маркер «reset» как новейшую запись (id −1) и отвечает «👌». Ничего не удаляется: следующий обычный текст начнёт с пустого контекста, но reply на любое сообщение до reset по-прежнему воскрешает его ветку.

### Что привязывается к id сообщений чата

| Сообщение в чате | Запись истории |
|---|---|
| Сообщение пользователя (текст/фото) | user-запись с его id |
| Каждый чанк ответа модели | своя assistant-запись с id этого чанка |
| Эхо транскрипции | user-запись с id эха; голосовое пользователя — алиас последнего чанка |
| Документ пользователя | user-запись `[file uploaded…]`; подтверждение бота — алиас |
| Сгенерированная картинка, отправленный файл | tool-response с id фото/документа |
| Tool-call без видимого ответа, результаты фоновых задач, саммари | id −1 |

### Прочее

- Контекст изолирован по паре (пользователь, чат): в группе у каждого участника своя история.
- Бот отвечает reply'ем только если сообщение пользователя само было reply; иначе — обычным сообщением. Так лента не засоряется цитатами.
- Идентификатор «разговора» для аналитики — корень ветки (`chat_id:id первого сообщения`): reply-ветки от одного корня — один разговор, `/reset` и устаревание — новый.

## 8. Автосуммаризация

- У каждой модели три порога: `short_term_memory_tokens` (когда сжимать), `summary_length` (размер саммари), `hard_max_context_size` (жёсткий предел, превышение — ошибка хода). Примеры: 32K / 8K / 64K для основной модели, 10K / 2K / 13–15K для дешёвых.
- Проверка выполняется при загрузке ветки и после каждого добавленного сообщения.
- Точка разреза: слева направо ищется первый индекс, начиная с которого хвост умещается в `short_term_memory_tokens / 2`. Хвост остаётся как есть, голова суммаризируется отдельным вызовом модели (для провайдеров без поддержки — кросс-провайдерный fallback на дешёвую модель). Промпт: «Summarize this conversation in N characters or less. Divide different themes explicitly with new lines. Return only text of summary, nothing else.»
- Саммари сохраняется как **обычная user-запись** истории с текстом `Summarized previous conversation:\n<саммари>`, id −1 и пустым списком предков. Следующие сообщения ветки ссылаются на неё, а не на исходные — сжатие необратимо для ветки (сырые записи остаются в базе и доступны через reply на них).
- Пользователь **не уведомляется**; стоимость вызова записывается в его usage. Настройка `auto_summarize` есть на пользователе, но в меню не выведена — сжатие всегда включено. Единственная видимая поверхность — пороги в карточке `/models`.

## 9. Доставка ответа: стриминг, форматирование, отмена

### Формат сообщений

- Ответы модели — Telegram Rich Messages (`sendRichMessage` с markdown в диалекте GFM: заголовки, таблицы, вложенные списки, code fences с языком, LaTeX, `<details>`). Лимит 32 768 символов, рабочий порог 30 000. Текст модели передаётся как есть, без экранирования.
- Если Telegram отверг разметку (ошибка «can't parse»), то же содержимое отправляется обычным `sendMessage` без parse mode. Ошибки других видов не глушатся.
- В истории ответ хранится как markdown-исходник.
- System prompt **ничего не говорит** модели про Telegram и правила форматирования — осознанный выбор: рендер полностью на стороне транспорта, промпт остаётся переносимым.

| Rich (markdown) | Plain (текст) |
|---|---|
| ответы модели (live и финал), результаты отложенных задач | ошибки, подтверждения загрузки |
| `/usage`, `/models`, карточки админа | эхо транскрипций, verbose-вывод tool calls |
| | сообщение плана агента, уведомление о запуске задачи, подписи к медиа |

### Стриминг и не-стриминг

- Настройка пользователя `streaming_answers` (по умолчанию **off**): без стриминга ответ генерируется целиком и приходит одним сообщением после «печатает…». Со стримингом — один из двух режимов live-вывода:
  - **(a) Редактирование на месте (по умолчанию).** Создаётся реальное сообщение с inline-кнопкой `Stop`, содержимое редактируется через `editMessageText`. Финальный ответ **редактируется в то же сообщение** (без удаления и пересоздания — нет мигания), клавиатура снимается.
  - **(b) Ephemeral draft** (флаг `RICH_DRAFT_STREAMING`, только приватные чаты). Промежуточный текст идёт через `sendRichMessageDraft` с `draft_id`: клиент анимирует его, статусы оборачиваются в `<tg-thinking>…</tg-thinking>`, кнопка Stop — нативная (`can_stop`). Draft живёт ~30 с, поэтому во время долгих tool calls он переотправляется каждые 20 с. Финал — отдельный `sendRichMessage`. Если draft-вызов отверг Telegram или чат групповой, ход продолжает в режиме (a).
- Правила показа промежуточного текста:
  - ничего не показывать, пока накоплено меньше 50 символов;
  - показывать без последнего (возможно недописанного) слова;
  - одинаковый текст повторно не отправлять;
  - при превышении 30 000 символов live-вывод замораживается с хвостом ` ⏳...` и больше не обновляется до финала.
- Финал длиннее порога режется **fence-aware сплиттером**: точка разреза ищется назад от порога сначала по `\n`, затем по `.`, затем по пробелу; если разрез попал внутрь блока ``` — блок закрывается в конце чанка и переоткрывается с тем же языком в начале следующего. Первый чанк — в live-сообщение, остальные — новыми сообщениями; **каждый чанк — своя запись истории** со своим id (reply на любой чанк работает).

### Пейсинг и flood control

- На ход создаётся один «шлюз»: между любыми live-обновлениями (draft или edit) не меньше 1 с. Обновление, пришедшее раньше, не выбрасывается, а откладывается: одна отложенная задача доставит **последнее** состояние, когда шлюз откроется (trailing-edge throttle — ничего не бёрстится, ничего не теряется). Шлюз общий для всех фаз хода, смены статусов и fallback draft → edit, чтобы они не сбрасывали интервал.
- `429 Too Many Requests` на live-обновлении не ломает ход: шлюз закрывается на `retry_after`, текст остаётся отложенным. Финальные сообщения (последний edit, чанки) делают одну паузу `retry_after` (не более 30 с) и повторяют отправку.
- Перед финализацией, очисткой и по завершении хода все отложенные обновления отменяются — ничего не «долетает» после ответа.
- Если во время редактирования Telegram вернул ошибку (сообщение удалено пользователем и т.п.), live-сообщение считается потерянным и следующий апдейт создаёт новое.

### Статусы: thinking и tool calls

- Блоки `<think>`/`<thinking>` в потоке распознаются (включая незакрытые). Пока модель «думает», live-вывод показывает `🧠 <последняя непустая строка размышлений, до 300 символов>` или `🧠 Thinking...`, если строка короче 10 символов. Из сохраняемого ответа размышления вырезаются полностью.
- При начале tool call live-вывод показывает подсказку: `Running <имя>...` по умолчанию или человекочитаемый статус инструмента (`Generating image...`, `Sending file...`, `Running bash command...`). Управляется настройкой `function_call_hints` (по умолчанию on). Подсказка живёт в том же сообщении/draft и затирается ответом.
- По завершении tool call при `function_call_verbose` (по умолчанию off) отдельным plain сообщением отправляется `Function call: <имя>(<аргументы>)\n\nResponse: <результат>`, обрезанное до 4080 символов.
- Ход может содержать **несколько финальных ответов** (режим агента: ответ → инструменты → ответ). После каждого финала live-вывод создаётся заново; для draft-режима `draft_id` уникален на фазу (`message_id * 100 + номер фазы`), чтобы клиент анимировал их независимо.
- Если ход завершился без финального текста (только tool calls), служебное live-сообщение удаляется, чтобы не оставлять в чате `Running …`.

### Отмена

- Два источника: inline-кнопка `Stop` (callback) в режиме (a) и нативное обновление `stopped_message_generation` в режиме (b). Обработчик должен быть зарегистрирован до старта polling, иначе тип обновления не попадёт в `allowed_updates`.
- Токен отмены — на пользователя. Нажатие Stop, когда ход не идёт, игнорируется.
- Поток от провайдера закрывается; **накопленный частичный ответ финализируется как обычный ответ** и сохраняется в историю с id сообщения. Недописанные tool calls (обрезанные аргументы) отбрасываются — инструмент не выполняется. В usage добавляется небольшая надбавка (20 токенов), т.к. провайдер не присылает usage прерванного потока.
- Цикл агента проверяет отмену в начале каждой итерации.

### Ошибки

- Необработанное исключение хода → reply на **последнее** сообщение батча: `Something went wrong:\n<тип>\n<текст>`. (При переносе — заменить на понятный текст, сохранив детали в логах.)
- Косметические ошибки Telegram (не удалось показать «печатает…», отправить verbose-вывод, эхо транскрипции) глушатся и не прерывают ход.
- Лимит последовательных tool calls в обычном режиме — 12; при превышении модель получает ошибку «too many successive function calls» текстом.
- Emoji-реакции на сообщения не используются; единственный эмодзи-ответ — «👌» на `/reset`.

## 10. Режим агента

Включается настройкой пользователя `agent_mode` (по умолчанию off). Меняется рантайм, а не транспорт: тот же стриминг, те же правила истории.

- **Цикл.** Итеративный, до 30 итераций; каждая итерация — вызов модели; tool calls выполняются, результаты возвращаются в контекст; текстовый ответ = финал (их может быть несколько за ход). Отмена проверяется в начале каждой итерации.
- **System prompt агента** (добавляется перед обычным): доводи задачи до конца, не останавливайся на предложениях; задавай вопросы пользователю только когда правда не хватает информации, и **все сразу**, а не по одному; у тебя есть bash/Python; будь краток и отчитайся о результате; веди план.
- **План как живое сообщение.** Инструменты «создать план», «обновить шаг», «получить план», «удалить план». При создании план отправляется в чат plain-сообщением вида `Plan: <название> [<статус>]` и строк `  <иконка> [<id>] <описание> (<статус>)`, иконки `○` pending, `►` in_progress, `✓` completed, `—` skipped. Каждое изменение статуса **редактирует то же сообщение**. Когда все шаги completed/skipped — план автозавершается. План переживает ходы (хранится на пользователе), новый план заменяет старый. Каждые 5 итераций модели подмешивается напоминание `<plan-reminder>` с текущим планом.
- **Фоновые подзадачи.** Инструменты «запустить под-агента» (возвращает id сразу) и «ждать завершения». Под-агент получает контекст разговора, свой лимит итераций (10) и таймауты; по таймауту возвращает частичный результат. Готовые результаты подмешиваются в контекст в начале следующей итерации как user-сообщение `<background-results>…</background-results>` плюс assistant-ack, обе записи с id −1. Незавершённые задачи отменяются в конце хода.
- **Отложенные задачи (scheduler).** Инструменты «запланировать» (once с временем на естественном языке или recurring с cron; время в `USER_TIMEZONE`), «список», «отменить». При создании сохраняется **снимок текущей ветки** (список id сообщений; хвост незавершённого tool-обмена, включая сам вызов планирования, отрезается, чтобы снимок был валидным контекстом). Планировщик опрашивает базу каждые 30 с. При срабатывании:
  1. состояние задачи обновляется **до** выполнения (once → выключается; cron → следующий запуск), чтобы не сработать дважды;
  2. в чат уходит plain `⏰ Scheduled task: <название>`;
  3. выполняется полный ход агента с контекстом из снимка и синтетическим user-сообщением `<scheduled_task_execution>` («задача сработала сейчас, это автоматический триггер, не планируй её снова, выполни и отчитайся; разговор выше — исторический контекст»);
  4. результат отправляется rich-сообщением и **записывается в ту же ветку** с его id — reply на результат продолжает разговор, в котором задача была поставлена.
- **Skills.** Папки с инструкциями (`SKILL.md` с name/description + произвольные файлы): личные в рабочем пространстве пользователя (агент пишет их сам) и общие read-only. В system prompt попадает **только каталог**: имя, описание (до 400 символов), путь; не более 50 записей; личный skill перекрывает общий с тем же именем. Тело skill модель читает сама инструментом чтения файла, когда решает, что он нужен. Сбой каталога — предупреждение в лог, блок опускается.
- **Web-агенты.** Поиск и скрейпинг — изолированные под-агенты с чистым контекстом и своей дешёвой моделью; основной агент видит только их итоговый текст.

## 11. Команды, меню и настройки

### Команды

| Команда | Действие | Видимость |
|---|---|---|
| `/reset` | маркер нового разговора, ответ «👌» | все |
| `/settings` | меню настроек | все |
| `/models` | карточка текущей модели + выбор | роль ≥ `USER_ROLE_CHOOSE_MODEL` |
| `/usage` | расход за календарный месяц | все |
| `/text2speech` | озвучить reply-сообщение или последнее | роль ≥ `USER_ROLE_TTS` |
| `/usage_all [-N]` | расход всех пользователей (N — месяцев назад) | ADMIN |

Список команд публикуется в Telegram глобально (набор для роли ADVANCED) и персонально для каждого пользователя по его роли. Команды регистрируются раньше общего обработчика, поэтому никогда не попадают в батч.

### `/settings`

- Сообщение с командой **удаляется**, бот присылает «Settings:» с inline-клавиатурой, по одной кнопке в строке. Три типа настроек:
  - **все опции видны**: текст кнопки `GPT-4.1 | <GPT-4o>` — текущее значение в угловых скобках, нажатие переключает на следующее;
  - **on/off**: `Streaming answers: On`;
  - **циклический выбор**: `TTS voice: onyx`, нажатие — следующее значение по кругу.
- Нажатие: перечитать пользователя из базы → переключить → сохранить → `editMessageReplyMarkup` (клавиатура перерисовывается на месте, без нового сообщения). Настройки, недоступные по роли, **не показываются** и дополнительно проверяются при нажатии. Последняя кнопка `Hide settings` удаляет сообщение меню.

| Настройка | Кнопка | Дефолт | Роль |
|---|---|---|---|
| `current_model` (быстрый выбор) | `<GPT-4.1>` | gpt-4.1 | `USER_ROLE_CHOOSE_MODEL` |
| `current_model` (полный список) | `Model: …` | — | ADMIN |
| `gpt_mode` | `GPT mode: assistant` | assistant | — |
| `use_functions` | `Use functions` | on | — |
| `image_generation` | `Image generation` | off | `USER_ROLE_IMAGE_GENERATION` |
| `system_prompt_settings_enabled` | `User info saving` | off | — |
| `tts_voice` | `TTS voice: onyx` | onyx | `USER_ROLE_TTS` |
| `voice_as_prompt` | `Voice as prompt` | on | — |
| `function_call_hints` | `Function call hints` | on | — |
| `function_call_verbose` | `Verbose function calls` | off | — |
| `streaming_answers` | `Streaming answers` | off | `USER_ROLE_STREAMING_ANSWERS` |
| `agent_mode` | `Agent mode` | off | — |
| `auto_summarize` | (не в меню) | on | — |
| `forward_as_prompt` | (не в меню) | off | — |

### `/models`

- Rich-карточка: `**Current model**`, полное имя, `**Pricing**` за 1M input/output токенов, `**Capabilities**` (streaming, function calling, image processing), `**Context configuration**` (порог памяти и длина саммари). Ниже — inline-кнопки моделей, доступных по роли (текущая помечена `< … >`), выбор редактирует карточку на месте; кнопка `Hide menu`. Модели с минимальной ролью «никому» скрыты от всех — способ отключить модель, не удаляя её.

### `/usage`

- Сообщение с командой удаляется. Rich-список за текущий календарный месяц: `**<модель>:** N prompt, M completion, $X` по каждой модели, `**Speech2Text:** N seconds, $X`, `**<image model>:** N images, WxH resolution, $X`, `**<tts model>:** N characters, $X`, `**Total:** $X`; кнопка `Hide`. Цена completion хранится вместе с записью usage (на момент вызова), остальное пересчитывается по тарифам.
- `/usage_all [-N]` для админа: по строке на пользователя `[telegram_id] Имя - @username: $X`, по убыванию, с итогом.

### Память о пользователе через инструмент модели

- При `system_prompt_settings_enabled` модели доступен инструмент «сохранить информацию о пользователе»: один текстовый аргумент, **полная перезапись** (не патч) сохранённого текста. Бот подтверждает `Saved User Info:\n<текст>` (или `Cleared User Info`). Текст вставляется в каждый system prompt как `<UserSettings>…</UserSettings>`. Так «запомни, что я пишу на Go и люблю краткие ответы» работает без отдельного UI.

### System prompt (обычный режим)

Слои, по порядку: персона из `gpt_mode` (по умолчанию «As an advanced chatbot Assistant, your primary goal is to assist users to the best of your ability.»; другие режимы — коуч, текстовая RPG — добавляются конфигом) → `Current date: <день недели, YYYY-MM-DD>` → добавки инструментов (каждый инструмент может дописать свою инструкцию) → `<UserSettings>`. В режиме агента спереди добавляется промпт агента, в конце — каталог skills.

## 12. Роли, онбординг, группы

### Онбординг и доступ

- Middleware на каждом сообщении: найти пользователя по Telegram id, при отсутствии — создать с ролью по умолчанию; синхронизировать имя и username, если изменились.
- Если роль ниже минимальной для доступа — reply «You currently don't have access to this bot. You will be notified once the admin grants you access.», обработчик не вызывается. Ответ приходит на **каждое** сообщение.
- При включённом админ-чате о новом пользователе туда уходит rich-карточка `#admin` с id, Telegram id, именем, username, ролью и inline-кнопками выбора роли. Нажатие меняет роль, перерисовывает карточку, публикует пользователю персональный список команд и, если доступ выдан впервые, шлёт ему «You have been granted access to the bot.».

### Роли

- Иерархия `STRANGER < BASIC < ADVANCED < ADMIN`; сравнение по порядку. Плюс служебная роль `NOONE` выше ADMIN, которой нельзя обладать — она используется как минимальная роль, чтобы скрыть модель или функцию от всех.
- Гейты (все по умолчанию BASIC): доступ к боту, выбор модели, стриминг, генерация картинок, TTS. У каждой модели и у каждого MCP-сервера — своя минимальная роль.

### Группы

- Отдельной групповой логики нет: ни фильтра по упоминанию, ни «отвечать только на reply боту». Бот обрабатывает всё, что до него доходит, — поведение в группах задаётся privacy mode в BotFather. При переносе стоит добавить фильтр «упоминание или reply на бота».
- Контекст изолирован по (пользователь, чат): у каждого участника группы своя история.
- Стриминг в группах — только режим редактирования на месте (drafts недоступны).
- Меню `/settings` и `/models` рассчитаны на личный чат.

## 14. Чек-лист переноса

Порядок, в котором зависимости складываются естественно.

1. **Батчер**: скользящее окно 300 мс на пользователя (лучше — на пару пользователь+чат), сортировка по `message_id`, якорь = первое сообщение, очередь батчей на пользователя.
2. **Классификация prompt / context-only** по таблице §2, флаг `force_prompt`, правило «батч — prompt, если хоть один элемент prompt», context-only путь без вызова модели.
3. **Хранение истории как дерева**: материализованный список предков, `tg_message_id` (−1 для невидимых), таблица алиасов, маркер reset, время активации.
4. **Выбор контекста**: снимок → reply (с алиасами, без окна, с обновлением активации всей ветки) → последнее сообщение в окне 1 ч → пусто.
5. **Разделение рантайма и транспорта**: события delta / final / tool started / tool completed, функция «отменено?», транспорт сохраняет ответ ассистента с id отправленного сообщения.
6. **Стриминг**: live-сообщение с кнопкой Stop, редактирование на месте, финал в то же сообщение; правила 50 символов / последнее слово / дедуп / заморозка на 30 000.
7. **Пейсинг**: один шлюз на ход, 1 с, trailing-edge, 429 продлевает шлюз, финал с одним повтором, отмена отложенных обновлений перед финализацией.
8. **Отмена**: токен на пользователя, закрытие потока, финализация частичного ответа, отбрасывание обрезанных tool calls.
9. **Rich-разметка с fallback** в plain при отказе Telegram; fence-aware сплиттер; каждый чанк — своя запись истории.
10. **Thinking и статусы tool calls** в live-сообщении; вырезание thinking перед сохранением; verbose-режим отдельным plain-сообщением.
11. **Форварды** с атрибуцией, сохранением картинок и правилом «forward ≠ reply».
12. **Голос**: транскрипция, эхо чанками, префикс `speech2text:`, алиас голосового на последний чанк, `voice_as_prompt`.
13. **Картинки**: самый большой размер, URL на прокси с токенами в имени, base64 только на запросе, понятная ошибка для моделей без vision.
14. **Суммаризация** с реальной записью саммари в ветке, без уведомления пользователя.
15. **Файлы** (при наличии рабочего пространства): сохранение, подтверждение с алиасом, caption как prompt, ошибка загрузки без потери вопроса, исходящие файлы с привязкой id.
16. **Меню настроек** на inline-кнопках с перерисовкой на месте, роли, онбординг через админ-чат, `/usage`.
17. **Режим агента** (по желанию): план как редактируемое сообщение, фоновые задачи, отложенные задачи со снимком ветки, каталог skills.
